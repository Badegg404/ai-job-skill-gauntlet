## 一、改动一：日志系统全套（commit e54fad9）

背景：原系统只有导入诊断日志（前端 reportDebug → /api/import-debug → import-debug.log），考核/面试/目录/设置等无日志，前端 JS 错误静默丢失，后端 handler 异常无 traceback。目标：全功能可追踪日志。方案文档：docs/日志系统规划方案.md。

### 1.1 后端（server.py，+235 行）

**新增日志基础设施（模块级，~60 行）：**
- `_make_json_logger(name, path)`：构造写 JSONL 行的 logger，RotatingFileHandler 单文件 2MB × 5 份轮转，失败降级 NullHandler
- `APP_LOGGER`：全局系统日志 → `~/.exam-center/logs/app.log`（启动/请求/未捕获异常）
- `activity_logger(uid)`：每用户活动日志 → `~/.exam-center/users/{uid}/logs/activity.log`，进程内 dict 缓存 + threading.Lock
- `log_json(logger, level, tag, msg, payload, **extra)`：统一组装 `{at, level, tag, msg, payload, ...}` JSONL 行，error→logger.error / warn→logger.warning / 其余→logger.info

**统一请求/异常日志（do_GET/do_POST 重写为包装器）：**
- 原逻辑移到 `_dispatch_get/_dispatch_post`
- do_GET/do_POST 统一 try/except/finally：异常 → 记 `http.uncaught` error（含 traceback 前 1500 字）+ 返回 500 JSON；finally → `_log_request` 记 method/path/durMs（>2s 记 `http.slow` warn，其余 `http.get/post` info）
- **注意：静态资源请求（/style.css、/exam.js 等）也会每行记 info**

**except:pass 审计补 warn（7 处）：**
- dir-rename 课程镜像改名失败、dir-delete 镜像删除失败、courses-index 读取损坏回退、course.json 读取损坏回退、reset-all 清理部分失败（计数）、批量导入 archive_import 失败、import-debug 写盘失败

**新增 3 个接口：**
- `POST /api/log`：前端批量日志上报，校验 uid + rows 为数组，逐行写 activity.log
- `GET /api/logs?uid=&file=activity|app&limit=`：诊断中心只读，limit 1~2000（默认 300），返回最近 N 行 + total + path
- `POST /api/logs-clear`：清空 activity/app 日志（unlink 主文件，**轮转备份文件 .1/.2 不删**）

**兼容：** 旧 `POST /api/import-debug` 接口保留（仍写 import-debug.log），前端 reportDebug 已改走 Logger，但旧调用点（tag 名）全部保留。

### 1.2 前端（web/logger.js 新增 88 行 + exam.js +181 行）

- `Logger.begin(kind)`：生成流程 sessionId（`kind_时间戳36进制`）

**exam.js 变更：**

## 二、改动二：重置后能力画像数据复活（commit 31ffdda）

### 2.1 现象与根因

用户实测：重置全部数据后，综合能力画像/考核记录等旧数据仍在。根因（已用真实 profile.json 佐证）：
- `saveState()` 是 fire-and-forget 的 `POST /api/profile-save`（11 个调用点，发出不等待）
- 用户点重置时，**重置前已发出的旧保存请求**可能晚于 `reset-all` 到达 → `_handle_profile_save` 无条件写盘 → 旧 state（含 abilityProfile/xp/history）写回 profile.json
- reload 后 `loadData()` 的 `state = {...state, ...profile}` 读回旧数据 → 复活
- 与历史「重置后徽章复活」同源（之前只 await 了 reset-all，堵不住"已发出的迟到请求"）

### 2.2 修复（时间戳墓碑）

**后端 server.py：**
- 模块级 `RESET_TS_FILE = "reset-ts"` + `is_stale_profile_save(udir, client_ts)`：
  - 无 client_ts / 无 reset-ts 文件 / 非法数值 → 不拦截（兼容老前端）
  - `client_ts < reset_ts` → True（丢弃）
- `_handle_reset_all`：删除数据后写 `(d / RESET_TS_FILE).write_text(str(time.time()*1000))`（毫秒时间戳）
- `_handle_profile_save`：请求体带 `clientTs`，stale 时记 warn `profile.stale-save-dropped` 并返回 `{"ok":true,"stale":true}`（不写盘）

**前端 exam.js：**
- `saveState()`：body 加 `clientTs: Date.now()`，且改为返回 fetch promise（可 await）
- `resetAllData()` 顺序改造：①重置内存 state 为初始值 → ②清 localStorage → ③await reset-all（删文件+写墓碑）→ ④await saveState()（空 state 落盘，clientTs 晚于 reset-ts 正常写入）→ ⑤reload

### 2.3 验证

- 后端 +6 测试（无 clientTs/无墓碑/旧 ts 拦截/新 ts 放行/非法 ts/端到端逻辑）
- 前端 +1 测试（saveState body 含数字 clientTs）
- 手工 e2e：造旧数据 → reset-all → 旧 clientTs 请求返回 `{"ok":true,"stale":true}`，profile.json 未复活；新 clientTs 正常写入

## 三、请重点审查的问题（按五维度）

### ① 逻辑正确性
1. `do_GET/do_POST` 包装器：异常路径先记 error 再 `_send_json(500)`，finally 里 `_log_request` 又记一行——**同一异常是否记了两行（http.uncaught + http.get/post）？** 可接受还是有重复噪音问题？
2. `log_json` 的 error→logger.error 映射与诊断中心按 level 过滤是否一致？
3. `is_stale_profile_save` 的数值比较：client_ts 与 reset_ts 都是毫秒级浮点/字符串，float() 转换是否稳？

### ② 数据正确性
4. JSONL 行字段（at/level/session/tag/msg/payload）与旧 import-debug.log 行格式（at/tag/payload）并存——诊断中心只读 activity/app，**旧 import-debug.log 不展示**，是否会造成排查遗漏？
5. `/api/logs-clear` 只删主文件不删轮转备份（.1/.2）——清空后读取仍可能看到备份？还是无影响（主文件重建）？
6. `activity_logger` 的 dict 缓存**无上限**——多用户/长期运行会累积 handler，是否该清？对单机应用影响多大？

### ③ 边界与竞态
7. **时钟一致性**：`clientTs = Date.now()`（浏览器）与 `reset_ts = time.time()*1000`（服务器）都取本机系统时钟，通常一致；但**若系统时间被改动/漂移，可能误判**（时钟偏慢 → 正常新请求被丢弃；时钟偏快 → 旧请求逃过拦截）。本机应用下风险多大？是否需要在文案/文档里说明或加容忍窗口（如 ±30s）？
8. 前端 Logger._flush 的 timer 单飞 + splice——并发 flush 是否有丢行/重复行？
9. 重置流程中（reload 前）若页面异步回调再触发 saveState（此时 state 已是空）→ 写回空数据，无害？是否有其它路径会在 reset-all 之后、空 state 落盘之前写入旧数据（**旧请求已发出且 clientTs 早于 reset-ts 之外的情形**）？
10. `/api/logs` 的 limit 上限 2000、默认 300——大日志下前端渲染量可接受？

### ④ 与现有机制一致性
11. reportDebug 旧调用点（llmJSON 内 15 处）零改动但行为从「立即单条 POST」变为「50ms 批量」——**llm-start/llm-ok 等诊断时效性**是否受影响（批量 50ms 延迟可忽略？）
12. `/api/import-debug` 保留但前端不再调用——是否有其它入口（旧版页面）仍依赖？
13. resetAllData 新顺序与 `loadData()`（reload 后从 /api/profile 读回 state）是否闭环：reset-ts 墓碑会不会**误伤后续正常使用**（用户重置后不 reload、继续操作）？
14. 首页诊断中心入口与既有 UI 风格/按钮组是否协调（纯样式问题，次要）？

### ⑤ 回归风险
15. exam.js 打点改动触及 11 个 saveState 调用点周边（startExam/submitAnswer/showResult/finishInterview/导入流程等）——是否全部回归验证过？测试 122 全绿是否覆盖这些路径？
16. `saveState` 从「同步函数内 fire-and-forget」改为「return fetch promise」——调用方无 await 的 11 处行为是否等价（无未处理 rejection）？
17. do_GET/do_POST 包装器对**所有**请求（含静态资源）增加日志写盘开销——本地单机性能影响？
18. reset-ts 墓碑与「多标签页同时操作同一用户」场景：标签页 A 重置，标签页 B 的挂起 saveState 被丢弃——B 的 state 会丢失吗？可接受？
